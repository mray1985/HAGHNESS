# Encrypted database backup recovery

October 2, 2026. ha/connected/backup_archive.py adds streaming AES-256-GCM encryption for database dumps. Document ciphertext alone does not protect ledger/profile rows in a database backup.

The archive contains a format header and random nonce prefix, sequential authenticated frames and an authenticated ending. Frame metadata and sequence are authenticated; truncation, altered frames, wrong keys and trailing bytes fail recovery. One-MiB frames bound memory use. Recovery uses a private sibling temporary file and publishes via an atomic hard link only after authentication and fsync; existing destinations are never replaced. Errors remove the temporary file. A crash may leave a private temporary file, which an operator must handle in its protected staging directory. The filesystem must support hard links. This does not authenticate the archive's provenance against someone holding its key.

The key is supplied separately, never stored in the archive. Administrators must maintain private staging-directory permissions, protected historical recovery keys and independent key backups. POSIX temporary files use mode 0600; Windows directory ACLs require separate administrative verification. A decrypted dump is private plaintext and must be handled as such before pg_restore. No routine client can call this module through an API.

The fictional recovery harness now encrypts its pg_dump output and restores from the authenticated decrypted archive. Saved DATABASE-RESTORE-EVIDENCE.json confirms all five tables match, six ledger events, both document versions and cross-profile denials. The harness intentionally retains synthetic plaintext working dump/restore files under ignored .connected-local for diagnostics; it does not prove an operational plaintext-retention policy. Actual client backup tooling must restrict and clean its staging files.

Tests cover multi-frame roundtrip, wrong-key cleanup, tampering, truncation, appended bytes, empty dumps, existing-destination preservation and failed atomic publication. Independent review identified early publication of partial files; the implementation now stages privately before atomic publication.

Hosted backup scheduling, consistent database/object-version inventory, off-host archive copies, 35-day/12-month retention enforcement and hosted recovery remain unfinished. This module is a recoverable encrypted dump primitive, not a complete backup system.

## Snapshot-linked encrypted document inventory

October 2: `backup_inventory.py` verifies every supplied immutable document version by fetching its exact object/storage version, checking plaintext length and SHA-256, and validating one continuous original/correction chain per profile/business/year/document. Missing predecessors, cross-scope links, cycles, forks, disconnected originals and duplicate object/version identities fail. The inventory records version metadata and object lengths, and binds them to the encrypted database archive's SHA-256. This operator utility is not exposed through the client API. Metadata includes profile and actor identifiers, so the manifest itself must be encrypted and access restricted.

The fictional restore harness holds a read-only repeatable-read transaction, exports its PostgreSQL snapshot, reads the inventory/version rows there, and runs pg_dump with that exact snapshot while the exporting transaction remains open. A third document upload commits afterward in a separate connection. Recovery still has the original two versions and matches all five snapshot tables, proving the later upload is excluded. The source database retains all three versions. This is a consistent database point, not a pause of application writes.

The harness verifies copied encrypted objects against the captured version rows, encrypts the resulting manifest with the separately supplied recovery key, recovers the manifest, checks its encrypted-dump digest before pg_restore, then verifies recovered database versions and decrypted object hashes against it. Saved DATABASE-RESTORE-EVIDENCE.json reports the actual local result. The recovered book profit remains $1,180 and unrelated-profile access remains denied.

This is local fictional evidence. Copying a local fixture directory does not implement hosted object capture; an operational capture must retain exact immutable versions, verify that every snapshot reference is available, and mark a bundle complete only after its dump, encrypted inventory and objects are durably stored together. A failed inventory leaves an incomplete working set, not a usable backup. It must not trigger retention deletion. Scheduling, off-host copies, externally recoverable historical keys and hosted restoration remain open. This harness intentionally retains fictional plaintext dump/manifest staging files in ignored .connected-local for diagnostics; that does not establish an operational plaintext cleanup policy.

## Completed recovery bundle gate

`backup_bundle.py` reserves a new private directory exclusively, encrypts the dump and each captured document with the separately supplied backup key, then verifies the captured encrypted objects against snapshot metadata. The encrypted inventory is published last and binds the database archive digest to every original/correction version. A directory without that inventory is incomplete and must not qualify for retention or a successful-backup status. Inspection authenticates the inventory, compares supplied restored database versions and verifies every captured document; marker presence alone is insufficient.

Normal and error cleanup removes only plaintext staging files owned by that invocation. A recovery target collision preserves the preexisting file. POSIX capture synchronizes the directory before and after completion publication; a final sync failure removes the owned completion marker. Windows directory ACLs and crash durability require their own operational verification. A process crash may leave private plaintext staging files, so an operator's restricted staging cleanup remains necessary. Failed capture directories are retained for diagnosis; this module performs no recursive deletion or retention enforcement.

Document archives wrap verified plaintext using the backup key independently of the original object-encryption key. `BundleObjects` is a recovery-only reader retaining the original logical object/storage references; it is not a Spaces uploader or production storage selector. Rehydrating hosted storage and reconciling provider storage-version identifiers require separate implementation and verification. No key is written into the bundle. Historical backup keys must remain externally recoverable.

The actual PostgreSQL fixture now creates and inspects a complete bundle. Its recovered dump matches the dump used for the verified database restoration, and the recovered database's Documents service reads original/corrected bytes from the bundle reader. Six bundle tests cover recovery, no plaintext in completed artifacts, failed capture without completion, existing-bundle preservation, wrong-key/altered-dump rejection, recovery-target collision and final sync failure. These six plus two PostgreSQL fixture-cleanup tests passed on actual Linux. Hosting, schedules, retention execution and disaster-recovery operations remain open.

## Callable consistent backup job

`backup_job.capture_backup` now joins the snapshot and completed-bundle components. An operator supplies the database connection, immutable object reader, external 32-byte backup key, a new private destination and an absolute installed pg_dump path. The job pins a read-only repeatable-read snapshot, gathers every document version and runs pg_dump against the same snapshot. It closes the transaction after the dump, captures immutable referenced objects, verifies the encrypted bundle and returns completion only after inventory publication. Source object versions must remain available; this module does not permit deletion.

Dump and plaintext staging live in a private temporary directory and are removed on normal execution or errors. Existing bundle destinations are refused. A failed capture can leave an incomplete encrypted directory for operator diagnosis. No scheduler or client endpoint invokes this job yet. Host/name/user are explicit so inherited PostgreSQL settings cannot silently select the child database. The database password is passed only through the child environment, not argv. Inline TLS private-key passphrases are unsupported and rejected; maintained private TLS-key handling remains an operator requirement. Subprocess output is suppressed so database details cannot reach application logs.

The actual fictional source job captured three current document versions and its completed bundle passed inspection. The older exported-snapshot fixture still restores two versions, excluding its later committed upload. This distinction verifies both a fixed recovery point and a new current capture. Failure tests cover rejected configuration, no password in child argv and staging cleanup after a failed dump. Scheduling, least-privilege hosted roles, external key access, off-host copy, provider rehydration and retention execution remain open.

## Read-only database role proof

The local recovery harness now runs the complete backup job through a freshly generated dedicated login. It has no superuser, database/role creation, replication or RLS-bypass attributes. Grants are limited to source-database CONNECT, HA schema USAGE and SELECT on HA tables/sequences. With the session's read-only setting disabled, actual INSERT, UPDATE, DELETE and CREATE TABLE statements still fail with insufficient privilege. Snapshot export and the pg_dump capture succeed with three current document versions. The fixture removes only its generated role and its grants afterward; existing test data and roles are unchanged.

`deploy/digitalocean/droplet/backup-reader.sql` supplies a fresh NOLOGIN group-role template with the tested read grants. It ships no account password and does not provision a service login. A deployment operator must grant it to a separately protected backup login, configure database CONNECT and TLS/network restrictions, and apply future-table/sequence default grants as each actual object-creating owner. The SQL has been verified through equivalent grants on the local fixture, not applied to hosted DigitalOcean. The key/object-store reader and off-host writer need separately scoped permissions; this database proof does not establish those controls.

## Disabled scheduler entry point

`python -m ha.connected.backup_runner` is the native Linux scheduler entry point. It requires `HA_BACKUP_ENABLED=true` plus complete database, source Spaces, external key, destination and executable settings. The source object interface supports reads only; use an independently restricted provider read credential. The backup key directory is separate from document keys. Both use mounted-key ownership/mode checks. The output directory must be private, operator-owned/root-owned and outside application code. Bundle names include UTC time, the validated non-secret recovery-key identifier and a random suffix. Retain that key reference when cataloging/copying bundles; the identifier is a lookup hint, while authenticated decryption proves that the correct key was supplied. No key bytes or passwords are emitted in status output.

The service/timer and blank disabled environment example are in deploy/digitalocean/droplet. The proposed timer runs at 03:30 UTC daily with up to 15 minutes jitter and catches missed starts. Its calendar expression passed the installed Linux systemd parser. It has not been installed/enabled or run against hosted resources. Provision a dedicated ha-backup OS user, a protected environment file, source-key/recovery-key directories with exact ownership and a private /var/lib/ha-backup directory. The oneshot sandbox grants writes only to that output directory, limits privileges and keeps key directories read-only. First run a manual capture and restoration with externally recovered historical keys before operator activation.

Runner tests verify explicit activation, rejection of incomplete settings, sanitized failure output and absence of a publication method from the read interface. They do not prove live provider permissions or hosted scheduling. The current runner captures locally; separate verified off-host copy, status monitoring, capacity measurements and retention enforcement remain required.


## Verified encrypted off-host copy primitive

`backup_transfer.copy_bundle` takes an operator-supplied separately scoped backup-store SDK client, bucket, external recovery key and snapshot versions. It inspects the local bundle, freezes ciphertext into private temporary staging, authenticates that staged bundle again, uploads encrypted database/documents to a fresh UUID prefix with private ACL and reads each artifact back to compare its complete size and SHA-256. Inventory is copied last. Private ciphertext staging is cleaned on success/error. The trusted private parent directory must have capacity for an additional encrypted bundle.

A failed transfer raises without successful status; uploaded partial prefixes remain for operator diagnosis and no deletion occurs. Failure while reading the final inventory can leave its remote filename present. Presence is never a completion or retention criterion: recovery must download and authenticate the complete bundle against restored versions, and operators must retain successful job status and the external recovery-key reference separately. A compromised store may change files after verification; authenticated disaster recovery remains required.

Five fictional-store tests cover matching ciphertext/private uploads/order, early and final readback failures, invalid local input and source mutation between inspection and staging. This is not live DigitalOcean evidence. The scheduler does not call this helper yet; backup-store configuration, provider permissions, integration, actual off-host download/restoration, monitoring and retention remain open.
